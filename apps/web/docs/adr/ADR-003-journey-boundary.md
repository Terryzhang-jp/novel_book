# ADR-003 · Journey 边界

- **状态**：已接受 · 2026-08-02 · 决策人：产品负责人
- **对应评审项**：`DOMAIN-MODEL-REVIEW.md` J1 / J4 / J6

---

## 定义

> Journey 是一段**有边界的现实外出经历**，承载时间、地点、意图、同行者与
> 相关 Moment。它是私人的：记录你为什么出发、看到了什么、回来后有什么不同。

## 决策

### J1 · 一日散步算 Journey —— 但只分两类

```
trip     多日或正式旅行
outing   一日外出、散步、短途体验
```

**不引入 `encounter`。** 一次偶遇更像 Moment 而不是 Journey 类型。
类型太多会让用户在开始记录之前先做分类作业 —— 那是产品在给用户派活。

### J4 · 可以自动提议，不能自动落库

系统按时间间隔 + 地理距离形成候选，**永远是提议**。用户确认、拆分或合并
之后才成为 Journey。

理由：自动分组一定会出错。一个会凭空生成条目的系统，用户很快就不再信任
它整理出来的东西。

### J6 · Journey 不能公开

Journey 是私人、原始、未筛选的体验容器。公开必须经过 Work → Publication。

这条约束的价值不在隐私，在**表达**：发布应该经过一次选择和组织，
而不是把原始体验直接倒出去。

## 其他确认项

| 问题 | 结论 |
|---|---|
| 多城市旅行 | 一个 Journey，内部靠 Moment 的地点自然分段。不做嵌套 |
| 时间 | 开始时间必填，结束时间可空（表示进行中） |
| 拆分 / 合并 | 必须支持 —— 是自动提议的必要配套 |
| 删除 Journey | **不级联删 Moment**。Moment 变成「未归类」，可重新归入其他 Journey |

删除不级联的理由：Journey 是**组织方式**，Moment 是**内容**。
删组织方式不该毁内容。

## 反例（这些不是 Journey）

- 「2025 年所有照片」→ 筛选条件
- 「我喜欢的建筑」→ 跨旅行的主题，应该是 Work
- 「秩父」→ 这是**地点**。「2025 年 9 月的秩父之行」才是 Journey

## 影响

- `journeys.type` 枚举只有两个值，新增需要新 ADR
- 自动分组的产物落在「候选」而非 `journeys` 表
- 无 `is_public` 列 —— 从数据结构上杜绝直接公开
